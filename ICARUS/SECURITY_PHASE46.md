# Phase 4.6 static security review

Reviewed new drone operations/schema/UI, boot/authority changes, integration hooks and command grammar against Phase4.5. Drones perform only local fictional simulation callbacks: they cannot execute shell commands, access a real drone, contact a network agent, read arbitrary files or alter system protection. No external asset/service/model calls are introduced. The gym is untouched.

New `drone:` command grammar accepts only build, autonomy on/off, bounded DRONE-1/2 launch to auto/0–24, and recall. Existing pairing, localhost host authorization, server lease/generation, acknowledgment and deduplication remain. Remote state is never uploaded as a replacement world. C01 safety/charge/knowledge checks occur in the authoritative controller. Main publish size limits remain; captured PNG omission uses explicit reconstruction labeling rather than increasing trust/size limits.

Captured images are bounded data:image/png base64 generated locally by the renderer and validated in saves. Replay uses Image/canvas; labels use textContent/DOM, not untrusted HTML insertion. No user-authored shell, executable media, external image URL or unrestricted path is introduced. New domains have bounded counts/coordinates/charge and reject unsupported versions; this does not certify the entire inherited import system against all malicious inputs.

The Windows .bat launcher invokes `py server.py` or `python server.py` from its own directory. It does not install dependencies. The server uses the existing browser-opening/local-host startup path. If dependencies are missing, the documented manual command `py -m pip install -r requirements.txt` can contact configured Python package indexes and modifies that Python environment. Users should inspect the retained launcher/requirements and choose a trusted Python environment. No elevated privileges, registry changes, services, scheduled tasks or antivirus exceptions are added by Phase4.6.

Inherited UMBRA can issue authenticated PC keyboard/mouse controls and Samsung TV network commands; those are real system/network capabilities, unlike fictional ship commands. Existing TV pairing/token storage, optional configured endpoints, local HTTP/SSE telemetry, LAN/Tailscale exposure and origin-based browser persistence remain. Do not expose the server to an untrusted network or share config/paired tokens. No independent cloud simulation or telemetry service is added.

Actual checks are documented in PHASE46_VALIDATION.md. Windows/native/device/real LAN/Tailscale and antivirus scans were not run. No antivirus protection was disabled or circumvented. The static review is not an antivirus certificate or an exhaustive penetration test.

Concrete inherited network behavior: server.py listens on0.0.0.0:8765 for LAN terminals; ordinary local HTTP/SSE is not transport-encrypted. `local_ip()` uses UDP connect to documentation address192.0.2.1:80 to ask the OS for a local route/address; it does not call send/sendto. Samsung control uses configured-TV wss port8002 with `ssl.CERT_NONE` for the TV's existing self-signed pairing path. That relaxed TV certificate validation is inherited, not new drone connectivity, and is limited to the configured TV transport. It is not evidence of physical TV testing. Existing PC macros can send real Ctrl+A/Copy/Paste/screenshot keystrokes, and require the existing authenticated client. None of these are fictional SOL shell privileges.
