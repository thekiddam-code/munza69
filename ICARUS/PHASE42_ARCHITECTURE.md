# Living Ship architecture

The browser's existing step/field controllers and save namespace remain authoritative. No separate simulation runs on UMBRA. Server, pairing, host lease, durable writer fence and desktop/mobile workspace remain Phase 4.1 implementations.

## Responsibilities

- **crew-life.js:** ordinary weighted choices, established stable preferences, physical shifts, conversations, private bounded activity ledger. Existing assignment budgets, supply collection, room capacity, movement and emergency priorities remain authoritative. A paid repair can explicitly close an activity using its genuine completion source.
- **crew-social.js:** additive version-1 save field. Numeric p.relationships remains the existing overall relation; typed trust/respect/resentment/loyalty/attraction are supporting dimensions, never copied over it. Memories require actual acquired sources or established personal experience records. Only actual participants gain social memories. Max 32 recent memories per active/historical person; per-pair dimensions bounded. Once-per-day mild resentment decay never deletes history or resets at episodes. Known encounter locations influence future ordinary room preferences; no clairvoyant tracking of friends.
- **crew-communications.js:** extends Knowledge's actual co-located conversation channel. Stress plus an uncertain acquired source can yield a seeded tentative interpretation. This is a separate reported-claim fact, referencing its premise; it carries no map/discovery/system payload and cannot rewrite world conditions. No private disclosure or recursive rumor chain. Any later legitimate delivery of the original (social contact, radio, debrief, records or recovery) marks the recipient's interpretation reviewed/withdrawn at the knowledge-acquisition boundary, without turning uncertain evidence into truth.
- **crew-decisions.js:** local debris-driven cleanup, real task-time recreation relief and source-linked post-repair inspections using the existing paid tools workflow (including its small ordinary engineering upkeep). Actual blocked assignments can request help at most once per activity/state and once per actor/day; the existing hierarchy decides repairs. Exhausted ordinary workers can release assignments through RepairPolicy; emergency assignments are protected. No new damage roll, resource production, automatic repair or incident quota.
- **crew-life-ui.js:** private preferences configuration in Creator > Crew > Roster. No adulthood/orientation is inferred. Mutual explicit adult preferences plus repeated trust and an actual eligible interaction permit each actor's independent private consent record. Withdrawal of preferences revokes participation. No defaults force couples and no settings edit fabricates a conversation.
- **embodiment.js / animation.js / cinematic.css:** read-only task cues and motion; cleanup, care, recreation reuse procedural rig; actual movement and incapacitation retain priority. No animation advances simulation.
- **knowledge-runtime / operational-view / SOL voice:** source-based reports distinguish direct observation, received report, inference and unverified claim. Private bonds/preferences never enter remote telemetry. Significant work reports use existing radio hardware/physical channels. Capture and Sunday compilation remain existing source-checked systems; no fabricated video.

## Registry and migration

Existing active crew and memorials initialize the registry from existing manifests/history. Dormant registration requires a retained, non-creator-authored source listing that name. Cap 128 registrations. Dormant profiles receive no active scheduler, body, knowledge or communications; no 80 invented crew are inserted into an old voyage. Registry API is a foundation, not a new crew recruitment UI. Existing core identity checks remain 20 established living+deceased; 100 active characters are unsupported.

Migration only adds absent fields. Original preferences, social memories, crew identities, p.relationships, resources, equipment, missions, research, dates and navigation survive. No schema/key reset. Exact save/reload and genuine old-backup tests are required. Clock/calendar/rate/pause handlers and host/remote authority are unchanged from Phase 4.1; known 20× investigation remains separate.
