# Phase 4.6 — Autonomous Exploration & Drone Reconnaissance

Baseline: Phase4.5 a996a6b. Frozen runtime: a22f2aca871e988a94cdd5083f8c99022da53460,137 files. This extends the existing core asteroid, crew task loop, economy, Knowledge, camera path and authoritative UMBRA protocol. No new universe, gym, ship rooms, clock, save namespace or native replacement.

## Authority and physical world

`drone-ops.js` owns the optional `state.droneOperations` domain. It runs once per actual simulation minute in the existing `step()` controller; `lastTick` makes re-entry idempotent. Production `Calendar.advance` and catch-up still invoke those same steps. Rendering/UI cannot advance drones. Real weeks, holiday1×, normal4× and approved selectable20× remain unchanged.

`ExpeditionWorld` remains the sole25-sector terrain graph. Existing Landing Shelf, industrial facilities, passages, slope/shaft/lift edges, caverns, borehole canon, military vessel and sealed23 remain. Drones respect actual passage closure, local visibility and powered lift gates; they do not fly through rock, reveal nonadjacent rooms, activate interlocks or call biological encounter/activation logic. There is no new planetary map. Near-core borehole/temporal canon remains creator reference until existing physical/sensor prerequisites provide evidence.

The physical deployment location is existing C01 Shuttle Bay, using a small unmanned deployment-port abstraction. Engineers collect paid components at existing C04, navigate the actual ship graph to C01, then assemble/service over performed work time. C01 power/gravity, safe operations and a stationary local ship are required. The recorded local approach takes50 ship minutes each way, matching existing expedition travel abstraction; it is not metric orbital flight physics. Active outbound/field/homebound drones prevent ship departure through the existing navigation planner. No spare free shuttle is created or consumed by this unmanned link.

The two-chassis limit is persistent, including lost chassis. The first drone can be assembled autonomously when received asteroid information exists, a qualified engineer is available and resources/safety permit. Additional assembly requires an authorized request. Reservations prevent two engineers paying for the same chassis. Crew energy, health, emergencies, maintenance, medical needs and accessibility retain priority. Interrupted consumed components are spent work, not automatically refunded or conjured back. Service uses actual parts/tools and performed engineering time; charging uses the existing finite energy ledger.

## Resources, navigation and risks

An assembled drone starts with zero charge. Charging transfers ship energy to100 bounded battery units (ten charge units per energy inventory unit); `charged - used = battery` is independently audited. Typical draws are.12/minute in approach transit,.35 during a terrain segment,.15 for local sensing, and.02 stranded standby. No battery/charge duplication on reload or repeated ticks. Propulsion/chassis condition wears during operation and actual radiation increases exposure wear; dense low-visibility conditions can degrade the optical sensor. Other sensor damage is persistent and honored. There is no random disaster quota, collision physics engine or guaranteed drone loss.

The drone uploads legitimate received drone surveys at its dock, observes the sector it physically reaches, and plans only through its onboard observed passages. It may enter one locally observed adjacent unknown sector. It returns after bounded new survey work, a received recall, elapsed mission budget, insufficient return reserve or sensor impairment. Return cost uses its observed connected path plus approach and emergency margin. A newly closed segment retraces elapsed travel before replanning; no endpoint teleport. Blocked returns, equipment loss or depletion can strand a drone. Total power loss during the exterior approach can leave an unrecoverable lost chassis at its recorded transit progress.

Existing crew expeditions can collect a stationary, co-located stranded drone if their genuine carrying capacity allows its4kg mass. The drone follows that expedition physically and is ingested only on actual return and a powered receiver/dock. If the carrying team is lost, the chassis remains at its last physical location instead of becoming permanently carried. A drone stranded partway through a segment is deliberately **not** collected by a team standing at the endpoint; a precise mid-passage salvage controller remains deferred. No automatic rescue or replacement.

## Observation, sensors and communications

Optical, thermal, mineral, radiation, structural and environmental channels each honor persistent sensor condition. They report the actual currently reached sector's existing environmental/utility/object data. Mineral sensing can identify an unclassified response from an actual mineral/crystal object, never invent chemistry, specimens, life or a breakthrough. Darkness and failed optics suppress visual identity/routes. Sensor readings are observations; research conclusions still require the existing evidence/experiment systems.

Radio is constrained by battery, radio/chassis condition, ship receiver power, blocked passages, depth/visibility and two connected-sector hops. Only physically placed, powered existing relays can extend a connected chain. A remote command is queued until a channel exists; autonomous return continues without remote guidance. The public interface retains last received status with a stale marker, rather than exposing the true disconnected position/battery. Lost feeds have no replacement image. Dock ingestion uses physical stored data even when a radio is damaged.

Onboard map records remain separate from received records because custody matters; both reference the **same existing sector IDs and graph**, not competing worlds. Receipt logs register actual observations with `Knowledge.observe`; crew learn them through existing legitimate records/communications. Existing Knowledge maps and history are retained. Received machinery condition can justify the existing industrial repair director. An actual received stranded report can justify one retrieval proposal per unchanged report; it cannot create an endless retry quota. Private local recovery observations pass through existing Knowledge delivery.

## Cameras and event provenance

The existing ObservationModel → ObservationUI → PixelCamera/FieldArt path handles drone feeds alongside ship/suit/lift/corridor cameras. Drone state includes its actual sector, segment progress, lighting and observed co-located field crew. Privacy/ship topology/Follow Crew remain. When a paused camera becomes visible again, its current received frame is redrawn; it no longer retains an offscreen unavailable placeholder.

A three-state onboard pre-event ring is retained. New physical surveys, changed sensor readings, obstructions and supported equipment/stranding events create bounded records with event ID, camera, mission, tick, location and reason. Up to two subsequent minute states follow (at most five frames). Ordinary travel does not create a continuous archive. When technically available, the authoritative host captures actual384×216 PNGs from the procedural camera renderer **at that processed simulation step**. These are captured simulation images, not physical footage, encoded video, or claims that a human watched a live feed during catch-up. Retained state DTOs permit separately labeled later reconstruction.

A disconnected drone's local ring/clips do not appear in received telemetry/history. Records transfer only through a working radio or recovered physical dock. Received records carry real receipt/source IDs and transfer method; duplicate receipt IDs are suppressed. UI playback distinguishes **CAPTURED PROCEDURAL FRAME** from **SOURCE-STATE RECONSTRUCTION** and never claims physical video.

Bounds: two chassis; three pre-event frames/device; eight local clips/device;24 received clips;40 mission summaries;25 onboard/received sectors. Each image is schema-bounded to80,000 characters. Host UI exposes up to eight received records. Remote telemetry exposes the latest received record with up to three frames and omits captured PNGs explicitly as necessary to stay within the existing125,000-byte working budget/131,072-byte publish cap. Those frames are displayed as labeled reconstruction; original captured PNGs remain in the host save. No protocol-size limit was bypassed. The original full historical journal can still grow through genuine events.

## Boot and persistence

`boot-screen.js` has no timer-based dismissal. Actual kernel/storage/systems/camera events determine readiness; exclusive Durable+server ownership is a separate writer stage, and Remote Deck Bridge authorization is separate again. The code input is never replaced/cleared by readiness updates. After genuine initialization, **ENTER ICARUS** becomes available. Readiness, retry, error and read-only states remain visible until that explicit action. Escape does not dismiss it. Opening status later follows the same explicit-entry rule. The continuous simulation may run behind the ready screen, as before; entering is not an extra simulation authority or clock.

`drone-schema.js` validates the optional domain, physical segments, battery conservation, bounded images/maps/records and engineering assignments. Legacy absence remains valid. Bootstrap/backup restore adds only empty operational metadata; it does not regenerate crew, voyages, histories, maps or organisms. Existing schema1 durable envelopes, atomic backup transfer, writer fences and namespaces remain. Older builds do not understand drone state: rollback uses the exported pre-upgrade backup.

`drone-ui.js` receives source-limited DTOs, presents survey/fog, devices, readings, history, camera selection and event playback. Commands use fixed server grammar and existing paired/acknowledged/deduplicated authoritative dispatch. UMBRA imports only UI/render dependencies, never drone simulation or the ship kernel. Existing Android/TV/LAN/Tailscale architecture is retained; native build awaits source recovery and physical-device tests remain separate.
